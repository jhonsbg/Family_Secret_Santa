## Orden de ejecución con acceso

1. Identificar en Vercel el equipo, el proyecto de pruebas, su plan, la protección y el historial de despliegues. Verificar que el proyecto ya está inicializado. Vercel puede clasificar un primer despliegue como Production aunque se omita `--prod`. Cualquier inicialización de este tipo requiere aprobación separada y, si se aprueba, usará una página estática sin la aplicación ni sus credenciales. [CLI de Vercel](https://vercel.com/docs/cli/deploy#prod)
2. Identificar el proyecto, la rama y la base `amigo_secreto_preview` en Neon. Comparar la identidad de la rama con los entornos de desarrollo y producción. Comprobar que las conexiones agrupada y directa pertenecen a la misma rama y que sus roles son distintos. Verificar que la base está vacía antes de aplicar las seis migraciones. Una rama derivada de un esquema con tablas preexistentes no sirve para este ensayo de instalación desde cero. [Ramas de Neon](https://neon.com/docs/manage/branches)
3. Ejecutar la inspección y la aplicación del [procedimiento de migraciones](E5.1-operacion.md#migraciones-y-configuración-de-postgresql) únicamente contra la base Preview verificada. Registrar los recuentos anteriores y posteriores y verificar el historial por hash. Guardar las dos conexiones en el archivo ignorado `.env.preview.ops` para mantenimiento y restringir su lectura.
4. Usar Node.js 24, `npm ci` y `npm run build:vercel`. Inyectar únicamente al ámbito **Preview** de Vercel la URL agrupada `DATABASE_URL_AUTH_PREVIEW`, el `AUTH_PEPPER` exclusivo y un `AUTH_ORIGIN` HTTPS canónico sin barra final si se usa un alias estable. Si se usa el origen automático, contrastarlo con el que el dashboard asigna al despliegue antes de probar formularios. La conexión directa queda en la estación de mantenimiento.
5. Confirmar **Vercel Authentication** y el alcance de protección para Preview antes de enviar el código. La documentación contempla **Standard Protection** y opciones de acceso separado para pruebas. La disponibilidad de enlaces revocables y sus cuotas se comprueban en la cuenta. La protección por contraseña en Pro puede tener costo. Usar cuentas autorizadas en los dos navegadores. Si el televisor no ofrece un navegador adecuado para iniciar sesión, conectarlo a un computador autorizado. [Protección de despliegues](https://vercel.com/docs/deployment-protection) · [Enlaces compartibles](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/sharable-links)
6. Confirmar el equipo y el proyecto vinculado, el historial y las variables de destino. Desplegar con `vercel deploy --environment=preview` desde la rama independiente. Registrar la revisión, el origen por HTTPS, el entorno que muestra Vercel, el resultado de compilación y el runtime. Comprobar primero el rechazo del acceso anónimo desde un navegador sin sesión de Vercel. [Entornos de Vercel](https://vercel.com/docs/deployments/environments)

## Matriz de validación en la URL de Preview

- **Alta y acceso.** Crear una partida ficticia y probar la cuenta del organizador. Abrir un enlace general en otro perfil, registrar solicitudes, aprobar una y rechazar otra. Registrar y activar un participante manual. Probar PIN, recuperación personal, recuperación asistida y sesión prestada. Confirmar que la recuperación y la revocación invalidan el acceso anterior.
- **Preparación y privacidad.** Cerrar inscripciones y configurar exclusiones. Ejecutar el sorteo y comprobar que dos inicios simultáneos producen una sola revisión. Verificar quién puede abrir cada sobre. Guardar deseos y comprobar persistencia tras recarga. Repetir el sorteo antes de la revelación y confirmar que los sobres anteriores pierden vigencia.
- **Intercambio.** Abrir el enlace de presentación en el navegador autorizado de un segundo dispositivo. Reabrir el panel con otra sesión del organizador y controlar turnos, adivinanzas, revelación, pausa, reanudación y cierre. Verificar que las identidades ocultas no llegan al navegador. Probar una desconexión del televisor y confirmar que al volver recupera la revisión actual.
- **Infraestructura y seguridad.** Probar la primera conexión tras inactividad, sesiones simultáneas en dos perfiles y recuperación después de una ejecución nueva. Usar un par de solicitudes en cada carrera, sin carga sostenida. Revisar `Secure`, `HttpOnly`, `SameSite=Lax`, `no-store`, origen de las acciones y ausencia de secretos en activos, respuestas públicas y logs. Registrar solo URL canónica, estados HTTP, duraciones y resultados.
- **Restauración.** Hacer una copia lógica de los datos ficticios de Preview y restaurarla en una rama o base vacía de ensayo con acceso independiente. Verificar historial, claves y recuentos, y comprobar que la rama activa sigue apuntada al mismo endpoint. [Importación y restauración en Neon](https://neon.com/docs/import/migrate-from-postgres)

## Verificaciones locales de la revisión

- Pasaron la instalación reproducible, lint, TypeScript, las pruebas unitarias y las suites de PostgreSQL de persistencia, PIN, permisos, recuperación, sorteo, sobres y revelación.
- `npm run build:vercel` pasó con valores ficticios de Preview. El control de compilación rechazó Production al recibir solo la configuración de Preview. La contraseña ficticia y el pepper ficticio se buscaron sin coincidencias en 76 activos públicos y páginas prerenderizadas. Este resultado corresponde al build local.
- Se aplicaron las seis migraciones en una base PostgreSQL local inicialmente vacía. El flujo de creación, activación, recuperación, sorteo, sobre y revelación pasó con el rol web de la guía de E5.1. Se comprobó que ese rol carecía de permiso para crear objetos en `public` o borrar partidas.
- Se restauró una copia lógica en una segunda base local. Contenía seis migraciones, una partida ficticia, tres participantes, tres asignaciones y un turno revelado. El ensayo de Neon sigue pendiente.
